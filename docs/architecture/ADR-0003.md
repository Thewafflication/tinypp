# ADR-0003: Initial Windows x64 target and explicit ABI

**Content type:** Architecture decision record

**Status:** Proposed

**Date:** 2026-10-31

## Context

WSP emphasizes Windows and TinyCC has target backends. DMC assets include
historical platform assumptions. The language standard does not select a
binary ABI.

## Decision Drivers

C++98 hosted completeness; audited TinyCC/DMC reuse; bounded initial target;
reproducible WSP evidence.

## Considered Options

1. One Windows x64 target with project C++ ABI.
2. Windows x86 for legacy reuse.
3. Immediate x86/x64/ARM64 vendor ABI compatibility.

## Decision

Propose Windows x86-64 as initial host and target, PE/COFF artifacts and
Windows x64 extern C calling convention. Define a versioned project C++ ABI
covering mangling, layout, vtables, member pointers, EH, RTTI, startup and
runtime ownership. Do not claim MSVC or DMC C++ binary compatibility. Validate
TinyCC object/linker and unwind feasibility at M1 before freezing this choice.
Following the 2026-11-01 roadmap update, use x64 for the first complete
vertical slice and bring up the same slice on Windows x86 and ARM64 before
broad language expansion. All three targets are required for planned
completion, with Debug/Release native verification. Keep host support
separate from target support; an initial x64 cross-compilation host is allowed.

## Rationale

The first x64 slice exposes semantics and runtime risks before the shared
target contract is exercised on x86 and ARM64. Early ports detect target
assumptions before broad language expansion. This proposal follows the
updated three-target roadmap; its ABI acceptance gates remain open.

## Consequences

### Positive

A staged three-target matrix and defined compatibility boundary.

### Negative

Legacy DMC binaries may be unusable; source and tool adapters may need
porting.

### Follow-up

REQ-0026; REQ-0027; REQ-0043. M1 demonstrates emission, C ABI calls,
cleanup/unwind and debugger operation; replan if infeasible.
