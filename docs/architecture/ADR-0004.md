# ADR-0004: Separate C++ semantics and target emission

**Content type:** Architecture decision record

**Status:** Proposed

**Date:** 2026-10-31

## Context

TinyCC is a C compiler whose parsing and emission are coupled. C++ adds
deferred instantiation, overloads, lifetime cleanup and exceptions.

## Decision Drivers

C++98 hosted completeness; audited TinyCC/DMC reuse; bounded initial target;
reproducible WSP evidence.

## Considered Options

1. Project C++ front end with typed lowering adapter.
2. Extend the C parser throughout.
3. Translate everything to textual C.

## Decision

Introduce token/source management, AST/types/symbols, semantic analysis,
typed lowering stages and an interface to the externally owned template
implementation/repository. Lower explicit object layout,
calls, cleanup, EH and RTTI through a documented target adapter. Reuse TinyCC
preprocessing, emission and linking after contract verification. Keep imported
changes controlled. Select host implementation language and edition after M1
experiments; product language remains C++98.

## Rationale

Retained structure supports delayed semantics and source diagnostics. Textual
C adds ABI, source mapping and EH complications as the primary architecture.

## Consequences

### Positive

Explicit ownership of semantics and backend contracts.

### Negative

More memory, integration and design work than one-pass emission.

### Follow-up

REQ-0008 through REQ-0025; REQ-0044. M1 prototypes scalar lowering and cleanup
contracts.

## Ownership clarification

Template implementation belongs to the existing separate project. AST/type,
lookup, instantiation-request, diagnostic and lowering contracts are Tiny++
integration responsibilities. No duplicate template engine is planned here.
