# ADR-0005: Runtime and hosted library integration

**Content type:** Architecture decision record

**Status:** Proposed

**Date:** 2026-10-31

## Context

DMC contains runtime and STLport candidates. Historical headers and binaries
do not establish a portable, complete library with the new ABI.

## Decision Drivers

C++98 hosted completeness; audited TinyCC/DMC reuse; bounded initial target;
reproducible WSP evidence.

## Considered Options

1. Port audited DMC/STLport source and adapters.
2. Write all libraries immediately.
3. Link arbitrary vendor C++ runtimes.

## Decision

The existing separate project owns templates and standard-library
implementation, selection and component verification. Tiny++ provides
compiler/runtime ABI contracts and integration tests against pinned external
deliveries. Share the DMC/STLport reuse findings with that workstream through
the controlled research note; do not start a competing library here.
Coordinate allocation ownership, initialization, EH, RTTI and destruction
interfaces. Runtime helper ownership is agreed at M1. Combined hosted claims
need both producer evidence and local integration results; core-only releases
identify their narrower scope.

## Rationale

Selective reuse follows the product objective without assuming binary
compatibility. A replacement library remains possible after a failed spike.

## Consequences

### Positive

Potential reuse by the existing external project without duplicate work.

### Negative

Locale, wide-character, exception and platform assumptions may dominate cost.

### Follow-up

REQ-0015 through REQ-0018; REQ-0022 through REQ-0033. M1 audits, M4 supplies
runtime, M7 verifies the externally delivered library.
