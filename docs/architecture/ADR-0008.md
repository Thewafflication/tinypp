# ADR-0008: Scalar compiler feasibility implementation

**Content type:** Architecture decision record

**Status:** Proposed

**Implementation:** Experimental; acceptance review pending.

**Date:** 2026-10-31

## Context

M0 final-edition reconciliation and external-project identification remain
open. Independent M1 feasibility work can still test the backend boundary.
MSVC 19.44 x64 and the pinned TinyCC sources are available locally. TinyCC's
Windows target writes ELF intermediate objects and links them into PE images.
It does not currently supply the proposed native COFF object interchange.

## Decision Drivers

- Exercise an owned C++ semantic front end rather than pass C++ to a C parser.
- Keep templates and the standard library in their existing external project.
- Preserve the submodule sources and retain native execution evidence.
- Expose unproved EH, object-format and debugger assumptions early.

## Considered Options

1. Typed scalar AST with a temporary C lowering adapter and TinyCC linker.
2. Treat TinyCC's C parser as the C++ front end.
3. Delay all implementation until every standards inventory item is closed.

## Decision

Use project-owned C++98 host source with CMake and MSVC x64 for the spike.
Retain scalar types, overload binding, lexical scopes and control flow in an
owned AST. Generate C only from this validated representation for the bounded
scalar adapter. The generated text is an internal feasibility interface;
it does not establish the final object-model, cleanup or EH lowering design
in ADR-0004. No raw user C++ is forwarded to TinyCC.

Build libtcc as a separate shared library from the pinned checkout without
editing it. Build support objects and copied headers in the project build
tree. Object emission produces ELF64 x86-64 intermediates; the TinyCC linker
produces PE x64 executables. Declare this format in help/documentation and
tests; COFF interchange with the MSVC linker remains unproved work.

The provisional scalar ABI is `tinypp_fn_<name>__<parameter-codes>`, using
`i` for int, `b` for bool and `v` for no parameters. Main uses `main`.
Scalar int/long and their unsigned variants use 32-bit target carriers,
with distinct semantic ranks and provisional codes i/l/j/m. Bool uses an int
carrier with values normalized to zero/one. This is a local experimental ABI, not vendor binary compatibility.
Freeze or replace it only after the full target ABI review.

Named namespaces extend the provisional symbol prefix with `tinypp_ns_`
and length-prefixed namespace/function components. This keeps `A_B::f`
distinct from `A::B::f`; global scalar symbols retain the earlier spelling.

Non-const reference parameters add `R` before their scalar type code and use
target-pointer carriers. Explicit C linkage uses the unmangled final name;
cross-namespace declarations of the same C symbol require matching signatures.
Reference lowering retains lvalue identity and evaluates address-side effects
once using scoped temporaries in the generated target-C adapter.

The driver rejects unsupported constructs and writes artifacts through a
same-directory temporary file. Publication preserves existing destinations.
The initial path interface uses Windows narrow strings and MAX_PATH limits.
No packaged distribution or library license-compliance claim is made.

## Rationale

An executable scalar path tests the most immediate integration assumption
without pretending that C lowering settles C++ lifetime, EH or ABI design.
Local C++98 host syntax also permits direct type-aware parser development.
MSVC has no strict C++98 mode; its successful build alone cannot establish
host-source edition portability.

## Consequences

### Positive

The project has native, reproducible compiler and target execution probes,
strict rejection boundaries, provisional cross-unit calls and owned semantics.

### Negative

No complete preprocessor, classes, references, EH, RTTI or final ABI exists.
Native COFF interchange and GDB-backed Debug failure evidence remain open.
The scalar adapter must evolve or be replaced for the remaining language.

### Follow-up

M1 retains its unwind, debugger and external-interface gates. M0 remains open.
Expand evidence by controlled fixture variants, preserving failures and exact
source/binary identities. Require separate Debug and Release results before
reporting this spike as tested in both configurations.

## Implemented module boundary

The owned AST declarations remain in frontend.hpp. frontend.cpp owns parsing
and scalar semantic analysis; lowering.cpp owns target-C construction; and
backend.cpp owns libtcc integration and artifact publication. Generated C
statement expressions preserve scalar assignment/update lvalue identity.
This separation does not close the final cleanup/EH lowering design gate.

Initial source translation is now isolated in source.cpp, retaining a physical
location map through trigraph replacement and line splicing. ast.cpp owns the
shared lvalue query. These modules extend the scalar spike without claiming
that macro expansion, include handling or the full translation model is done.
