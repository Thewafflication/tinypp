# ADR-0010: Assess Digital Mars compiler-source reuse

**Content type:** Architecture decision record

**Status:** Proposed

**Date:** 2026-10-31. Direction updated 2026-11-01.

## Context

DigitalMars/Compiler has been added separately from the dmc distribution.
The pinned source contains C++ semantic, lookup, class, EH and RTTI modules,
largely written in D and coupled to shared backend representations. This
changes the original availability finding behind ADR-0002. Our current
owned scalar front end and TinyCC adapter remain operational.

README and CI build prerequisites differ, and the documented C++ compiler
build is Win32. Neither source presence nor modern backend modules establish
a reusable Windows x64 C++ compiler. Templates and the standard library
remain owned by the user's existing external project.

## Decision Drivers

- Reduce independent semantic implementation where audited reuse helps.
- Preserve reviewed C++98 behavior and explicit defect decisions.
- Maintain native Windows x64 execution and WSP evidence identities.
- Keep type, lifetime, emission and external-project boundaries deliberate.
- Measure D/toolchain/backend coupling before accepting migration cost.

## Considered Options

1. Selectively adapt audited semantic and runtime-contract components.
2. Integrate a D semantic component behind a versioned ownership interface.
3. Use a process-isolated DMC semantic worker with an owned typed handoff.
4. Replace the existing front end and backend with the full legacy compiler.
5. Retain the independent implementation and use the new source as reference.

## Decision

Select a process-isolated DMC semantic worker as the integration direction.
Retain the owned Tiny++ driver, a versioned typed handoff and TinyCC target
adapters. DMC owns its private parser/type/symbol state within one worker
process per translation unit and target configuration; no borrowed pointers,
D layouts or C++ implementation structures cross into Tiny++.

Adopt the DMC front-end semantics as a unit behind this boundary rather than
require individual D modules to behave as independent shared libraries. The
owned scalar front end remains a regression baseline until migration gates
pass. The existing DMC native backend and its adaptations remain feasibility
and comparison tools; their success does not select the production backend
or establish the project C++ ABI on x86, x64 or ARM64.

The first experimental handoff exports copied, resolved function/type
signatures. It is not function-body IR and cannot generate a program by
itself. See the [handoff contract](semantic-handoff.md). Extend the boundary
to declarations, typed control flow, object/lifetime operations, EH/RTTI and
source diagnostics before routing production compilation through it.
Target properties must be supplied through the shared target contract;
legacy DMC target assumptions are not silently adopted by all adapters.

Templates and the standard library retain their existing external ownership.
Their delivery, instantiation requests, lookup and runtime interfaces must be
pinned and integrated. Building upstream dtemplate.d for this experiment does
not allocate a second template implementation to Tiny++ or qualify export.

Continue isolated source builds with recorded tool/source identities and
file-level grants. The engineering direction is selected; this ADR remains
Proposed, and production replacement, M1 closure and conformance acceptance
remain gated on the evidence below.

## Rationale

The source-built compiler already provides measured lookup, class and native
object behavior. Shared scope/configuration state and reference-counted types
make an in-process ownership boundary costly. Configured import traces reach
24–26 local files per inspected semantic module. An exploratory x64 dtype
component compiled but a real type-qualification call linked with 45 unresolved
symbols, including parser, template, allocation and target services. This is
an unresolved extraction attempt, not proof that a library is impossible.

Process isolation lets us reuse the known build while keeping compiler state
and allocation private. A copied, validated protocol gives the owned IR and
target adapters a deliberate boundary. It avoids committing every target to
DMC's emitter and runtime. It still requires substantial IR export, target
abstraction, runtime work and standards validation; no schedule reduction is
claimed from the signature prototype alone.

## Consequences

### Positive

M0/M1 can evaluate real source reuse with pinned notices and observable
interfaces. Existing implementation and external ownership are preserved.

### Negative

Feasibility work requires an additional D build chain and dependency tracing.
No schedule reduction is claimed before successful probes and review.

### Follow-up

Execute DM-01 through DM-05 from the assessment. Update this proposed ADR
with measurements and a selected implementation boundary before integration.
Retain all existing scalar regressions; add independent type, lookup and
normal/exceptional lifetime partitions before accepting imported semantics.

## Feasibility evidence update

An isolated source build now succeeds with a recorded Cent field-alias
adaptation, using DMD 2.092.0 and the pinned DMC distribution tools. The
source-built 9.01.0n compiler passes ten compile-only and eight native Win32
partitions. Pristine build reproducibility, extraction closure and Tiny++
x64 adaptation remain open. This evidence does not select or accept a full
front-end replacement; the Decision and Proposed status remain unchanged.

Additional output-copy adaptations pass 44 x64 MSVC C ABI partitions with
and without target optimization, including POD value copies and returns.
POD lowering follows inline expansion and preserves semantic parameter types;
caller copies have explicit alignment. A later guarded publication adaptation
passes the same 44 cases without -Nc, including optimized/debug emission.
Strict mode, nontrivial classes and x64 EH/RTTI are unverified.
These limits preserve the need for measured extraction and architecture review.

An assertions-enabled build also passes all 44 optimized x64 cases with
debug information after guarded relocation-width and CV8 adaptations.
The optional DIA fixture resolves three function names and source lines;
aggregate records are opaque and member/variable fidelity is unverified.
This is additional feasibility evidence, not debugger qualification or
acceptance of the proposed architecture.

Configured SCPP import traces for six semantic modules reach 24–26 local
source/interface files each. Shared scope, parser/configuration state and
reference-counted types require an explicit session/ownership contract;
these counts are not extraction or linker closure. Cross-unit object probes
and retained x64 EH/RTTI link failures now sharpen the runtime boundary.
Those observations did not yet select a boundary. The updated Decision now
selects the process-worker direction; production body/IR and runtime
integration remain open. Isolated native execution is not Tiny++ integration.

The expanded 50-case x64 suite passes optimized/debug and unoptimized,
including cross-unit nontrivial copies and adjusted virtual dispatch.
Guarded ES-mask, constructor-preserving argument lowering and explicit local
alignment adaptations retain existing Win32 regressions. Optional x64 EH/RTTI
probes compile but fail on real runtime dependencies. These results supported the subsequent process-worker selection; they do
not establish production integration of the DMC front end.

## Production migration gates

1. Verify signature ownership/versioning and failure controls, then define and
   exercise typed function-body and source-diagnostic protocols. No address or
   private structure may escape the worker session.
2. Export calls, class identities/layout requests, construction/destruction,
   normal and exceptional cleanup, RTTI and explicit target-property queries.
   Unsupported operations fail closed; no successful native DMC object may
   substitute for an unimplemented Tiny++ handoff operation.
3. Consume the handoff into owned IR and emit through the selected target
   adapters. Run the existing scalar suite through this path, retaining the
   independent front end as a comparison until semantic regressions resolve.
4. Pass the shared class/EH/RTTI vertical slice on x64, then x86 and ARM64;
   measure startup, memory, protocol size and diagnostics before replacement.
5. Verify the external template/export/library interfaces and standards gates
   for the delivery being claimed. Review provenance and deployment packaging.

The exploratory dtype component artifacts are under output/dmc-bridge-discovery/
f9927f8797b24a6396350b93510eee88; they are discovery evidence, not a qualified
reproducible library-build gate. The selected worker direction can be revised
if measured handoff or target-adaptation costs invalidate it.

The signature worker now passes nine producer/consumer cases on each of x86
and x64: six positive metadata partitions and three controls. Eight programs
per target execute natively with result 42; the I/O failure control requires
nonzero worker status. Record layout differs as expected for a pointer-bearing
class (8 bytes/alignment 4 on x86; 16 bytes/alignment 8 on x64). The consumer's
18 protocol controls pass. These establish a copied signature boundary, not
function-body IR, native EH/RTTI handoff or ARM64 support.

## Typed body pilot update, 2026-11-04

A scalar body protocol now exports local bindings, typed expressions and CFG
edges before inline/ABI lowering. An explicit semantic-only mode returns
without native function emission after releasing the copied body state.
The owned importer emits checked C and TinyCC objects; the native executable
links only those objects. The experimental compile_worker.py command accepts
ordinary .cpp inputs, standard zero-argument main and cross-unit scalar calls.
It preserves existing output files and retains each compilation attempt.

The worker's native emitter asserted on a weighted eight-argument function
after export. The original failed attempt remains evidence; semantic-only mode
completes successfully and the owned/TinyCC path executes that same program.
This validates the selected separation without claiming to fix the upstream
native register bug. Class/lifetime/EH/RTTI body operations, full diagnostics,
external bindings and the x86/ARM64 body emitters remain migration gates.
